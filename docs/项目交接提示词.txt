接口缺陷：
DSH 的 tools/result 事件签名是 (exec, result)。exec 是工具名、参数、callId、Agent、signal 等调用身份；结果位于第二参数。
上游 index.js 只接收 execution，再交给 recordResult；guard-state.js 却从 execution.result/output 读取结果，导致结果被视为 unknown。
默认读文件→修改文件→再次读取：文件实际已经变成 after，第三次调用（第二次读取）却在工具函数执行前被 LOOP_GUARD_DUPLICATE 拦截。

诊断桥接：
native-harness.mjs 的 --bridge 将第二参数映射为 callback({ ...execution, result })，只给原插件监听器传一个新对象，没有修改原生 exec。
桥接后读改再读恢复正常。它是 B 组诊断对照，尚未应用到工作副本的正式实现，更不是新语义策略。
因此桥接模式的原生观察日志仍显示 exec has result field = false，属于预期行为。

仍存在的策略缺口：
- 实际后台进程仍在 running 时，原版第二次 job_output 被拦；桥接后第三次被拦，进程随后正常完成。
- 同一操作仅更换 description 等展示字段，可以绕过重复组。原版仍有默认 64 次无进展总预算，不要宣称无限运行。
- 仅修结果接入后，相同失败测试的时间戳/耗时变化可被当成进展。8 次实际失败测试均被放行，固定输出控制则第三次被拦。这是桥接后的条件性缺陷，不是未修改原版直接发生的漏检。
- 工具层 isError=false 可以和程序 exitCode=1 同时成立，需要区分工具返回成功、程序结果、有效证据和任务进展。
另发现停止词语境及 JSON 括号输出误拦，先留作独立补丁候选，主线不扩张。
